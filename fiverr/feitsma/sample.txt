I have an Express.js + TypeScript application using Mongoose/MongoDB. I already have `Shipment` and `Route` Mongoose schemas/models, which I will import into the new route-optimization service/handler.

I need you to design and implement a **production-quality, efficient dynamic route optimizer** for delivery and collection shipments.

Do NOT implement this as a simple nearest-neighbor algorithm. The problem must be treated as a **dynamic capacitated vehicle-routing problem with pickups, deliveries, depot replenishment, depot unloading, urgency, shipment staleness, and route feasibility constraints**.

The implementation should prioritize correctness, efficiency, maintainability, and predictable behavior.

---

# 1. Request

The main Express handler receives:

```ts
{
  vehicleCapacity: number;
  deliveryShift: string;
  routeType: "mixed" | "number";
  routeNumber?: string;
  userId: string;
}
```

The main handler should dispatch to:

```ts
handleMixedRoute(...)
```

or:

```ts
handleNumberedRoute(...)
```

depending on `routeType`.

Use normal arrow functions throughout the implementation.

# 4. Depot

All routes start at:

```ts
const DEPOT = {
  lat: parseFloat(process.env.DEPOT_LAT ?? "52.4002"),
  lng: parseFloat(process.env.DEPOT_LNG ?? "4.6417"),
};
```

The depot is not just the starting point.

Treat the depot as a valid route operation that may occur during the route for:

1. Loading additional delivery boxes.
2. Unloading excess collected boxes.
3. Recovering from future capacity constraints.
4. Making otherwise infeasible shipment sequences feasible.

Represent depot operations explicitly in the generated route.

For example:

```text
DEPOT
→ Shipment A
→ Shipment B
→ DEPOT_REFILL
→ Shipment C
→ Shipment D
→ DEPOT_UNLOAD
→ Shipment E
```

# 5. Core vehicle state

The algorithm must maintain an explicit vehicle state throughout route construction.

Use something similar to:

```ts
interface VehicleState {
  currentLocation: PositionLatLng;
  currentLoad: number;
  initialLoad: number;
  maxLoad: number;

  totalDistance: number;
  depotVisits: number;

  completedShipmentIds: Set<string>;
}
```

At every point:

```ts
0 <= currentLoad
```

and:

```ts
currentLoad <= vehicleCapacity
```

must always be true.

Never create a route containing an impossible vehicle load.

When:

```ts
routeType === "mixed"
```

query shipments using:

```ts
{
```

Use `userId` as the owner reference.

The returned shipments are candidates for route creation.

The generated mixed route does NOT necessarily need to contain every available shipment.

The optimizer should select shipments that can be incorporated into a high-quality feasible route.

# 7. Mixed-route objective

The mixed route optimizer must balance:

1. Urgency.
2. Shipment staleness.
3. Distance.
4. Vehicle capacity.
5. Collection opportunities.
6. Future delivery feasibility.
7. Number of depot visits.
8. Total route distance.

Do NOT simply sort by:

```ts
distance
```

and do NOT simply sort by:

```ts
createdAt
```

Instead, use a dynamic candidate-scoring system.

---

# 8. Shipment priority

Urgent shipments should have a much stronger priority than normal shipments.

The optimizer should recognize:

```ts
isUrgent === true
```

as a high-priority condition.

Staleness should also affect priority.

Older shipments should generally receive higher priority than newly created shipments.

However:

**Do not allow staleness or urgency to blindly override capacity feasibility.**

A shipment must still be physically feasible.

---

# 9. Candidate generation

At every route step, generate a set of currently feasible candidate operations.

Candidates can be:

```ts
type Candidate =
  | {
      type: "shipment";
      shipment: ShipmentDocument;
    }
  | {
      type: "depot-refill";
    }
  | {
      type: "depot-unload";
    };
```

For shipments:

### Delivery feasibility

A delivery is immediately feasible when:

```ts
currentLoad >= shipment.boxQuantity
```

### Collection feasibility

A collection is immediately feasible when:

```ts
currentLoad + shipment.boxQuantity <= vehicleCapacity
```

Do not visit a collection if it would exceed vehicle capacity.

---

# 10. Important dynamic inventory rule

Do NOT assume all delivery boxes must be loaded at the depot at the beginning.

Example:

```text
Vehicle capacity = 20
```

Suppose deliveries require:

```text
A = 5
B = 4
C = 6
D = 3
```

and collections provide:

```text
E = 8
F = 5
```

The vehicle may start with fewer than:

```text
5 + 4 + 6 + 3
```

boxes if collections later provide inventory.

The optimizer must calculate the minimum practical initial load based on the planned route.

---

# 11. Future feasibility / look-ahead

Do not choose the next shipment using only the current state.

Use a **look-ahead window of approximately 2–4 future stops**.

For every candidate shipment, estimate how useful the candidate is for subsequent shipments.

For example:

```text
Current load = 2
Capacity = 10

Nearby:
Collection A = +5
Delivery B = -6
Delivery C = -4
```

Visiting Collection A may be preferable even if it is slightly farther away because it enables future deliveries.

The algorithm should ask:

> If I take this candidate now, how many of the next most valuable shipments become feasible?

Use this future feasibility as part of the candidate score.

Do not perform an exhaustive search over every possible route permutation.

The look-ahead must remain computationally bounded.

---

# 12. Candidate scoring

Create a scoring function similar to:

```ts
calculateCandidateScore(...)
```

The score should consider:

```text
+ urgency
+ staleness
+ pickup usefulness
+ future feasibility
+ geographic proximity
- travel distance
- unnecessary depot visits
- capacity risk
```

A candidate score should be deterministic and explainable.

For example:

```ts
interface CandidateScore {
  urgencyScore: number;
  staleScore: number;
  distanceScore: number;
  pickupBenefitScore: number;
  futureFeasibilityScore: number;
  capacityScore: number;
  depotPenalty: number;
  totalScore: number;
}
```

Do not hard-code arbitrary numbers without structuring them as named configurable weights.

For example:

```ts
const ROUTE_WEIGHTS = {
  urgent: ...,
  stale: ...,
  distance: ...,
  pickupBenefit: ...,
  futureFeasibility: ...,
  capacityRisk: ...,
  depotPenalty: ...
};
```

Make these weights easy to tune later.

---

# 13. Priority tiers

Use a predictable priority hierarchy.

A recommended strategy is:

```text
Tier 1: urgent and feasible
Tier 2: highly stale and feasible
Tier 3: normal shipments
```

Distance optimization should occur within those priorities rather than allowing a nearby normal shipment to constantly beat a critical urgent shipment.

However, never select an infeasible shipment merely because it has higher priority.

---

# 14. Distance calculation

Do not use Google Distance Matrix.

Unless explicitly requested later, calculate geographic distance locally using the Haversine formula.

Example:

```ts
calculateDistance(a, b)
```

should return distance in kilometers or meters.

Cache calculated distances so the same pair is not repeatedly recalculated.

Use a distance cache such as:

```ts
Map<string, number>
```

or:

```ts
Map<string, Map<string, number>>
```

with a stable key generated from location/shipment IDs.

This is especially important when the number of shipments becomes large.

---

# 15. Depot refill logic

The vehicle should return to the depot when:

* no valuable delivery is feasible;
* the next important delivery requires more boxes than currently available;
* future feasibility requires replenishment;
* a depot visit reduces overall route inefficiency;
* the route cannot progress otherwise.

When returning to the depot for delivery inventory:

```text
vehicleLoad += requiredBoxes
```

but never:

```text
vehicleLoad > vehicleCapacity
```

Only load as many boxes as reasonably required.

Do not automatically fill the vehicle to maximum capacity unless doing so improves route efficiency.

---

# 16. Depot unload logic

If collected boxes cause the vehicle to approach capacity and those boxes are not immediately useful, the optimizer may return to the depot to unload them.

Example:

```text
capacity = 10
currentLoad = 8
collection = 2
```

Collection is feasible:

```text
8 + 2 = 10
```

If future collections/deliveries require additional capacity, consider:

```text
→ DEPOT_UNLOAD
```

before the next collection.

Minimize unnecessary unload trips.

---

# 17. Mixed route termination

Continue route construction until:

1. no additional shipment can be beneficially incorporated;
2. remaining shipments cannot be feasibly handled under current constraints without violating the intended route objective;
3. or the optimizer determines that the route should end.

The selected shipments must be saved into the Route document in their exact execution order.


```ts

```

Find all relevant shipments associated with:

```text
OwnerRef = userId

```

All required shipments associated with the route number must be incorporated.

Do not omit shipments simply because the vehicle initially lacks sufficient capacity.

# 19. Numbered route objective

For numbered routes, prioritize:

1. Every shipment must be completed.
2. Never violate capacity.
3. Minimize total distance.
4. Minimize depot visits.
5. Preserve urgent/stale priority where reasonable.
6. Use collections intelligently to provide boxes for later deliveries.

The numbered route is therefore different from the mixed route.

Mixed route:

```text
Select the best feasible subset.
```

Numbered route:

```text
Include everything while finding the best feasible sequence.
```

---

# 20. Numbered route capacity overflow

If a numbered route requires more boxes than the vehicle can carry simultaneously, automatically insert depot operations.

Example:

```text
DEPOT
→ Delivery A
→ Collection B
→ Delivery C
→ DEPOT_REFILL
→ Delivery D
→ Delivery E
→ DEPOT_UNLOAD
→ Collection F
→ Delivery G
```

The algorithm must determine the minimum practical number of depot visits.

Do not create unnecessary depot trips.

---

# 21. Dynamic pickup/delivery dependency

The optimizer must understand that collections can enable later deliveries.

Example:

```text
Capacity = 10
Current load = 3

Delivery A = 6
Collection B = 5
```

Delivery A is currently infeasible:

```text
3 < 6
```

but Collection B may make it feasible:

```text
3 + 5 = 8
```

Therefore:

```text
Collection B
→ Delivery A
```

may be a superior sequence.

The algorithm must explicitly model this kind of dependency.

---

# 22. Post-route improvement

After the first feasible route is generated, run a lightweight improvement phase.

Do NOT perform exhaustive optimization.

Use local-search techniques such as:

```text
2-opt
swap
relocate
```

where appropriate.

Every route modification must preserve:

```text
vehicleCapacity
shipment uniqueness
delivery/collection feasibility
depot requirements
```

For example:

```text
Initial:
A → B → C → D → E

Improved:
A → C → B → D → E
```

is acceptable only if the vehicle inventory remains feasible throughout the changed sequence.

The improvement phase should aim to reduce:

```text
total distance
```

and, where possible:

```text
depot visits
```

without significantly harming urgency/staleness priorities.

---

# 23. Initial load calculation

Create a function:

```ts
calculateInitialLoad(...)
```

The initial load should be the minimum practical number of delivery boxes required to begin the selected route.

Do not automatically load the sum of all delivery `boxQuantity`.

The calculation should consider:

* early deliveries;
* nearby collections;
* future collections;
* vehicle capacity;
* planned depot visits.

The result must satisfy:

```text
0 <= initialLoad <= vehicleCapacity
```

---

# 24. Vehicle-state transitions

Every shipment operation must update vehicle state.

Delivery:

```ts
currentLoad -= boxQuantity;
```

Collection:

```ts
currentLoad += boxQuantity;
```

Depot refill:

```ts
currentLoad += refillQuantity;
```

Depot unload:

```ts
currentLoad -= unloadQuantity;
```

Update:

```ts
maxLoad = Math.max(maxLoad, currentLoad);
```

after every state transition.

Do not repeatedly query MongoDB while constructing the route.

Prefer:

```text

→ save final route
```

where practical.

Create appropriate MongoDB indexes for commonly filtered fields such as:

```ts

```

Do not introduce N+1 database queries.

# 28. Algorithmic efficiency

Do NOT use:

```text
O(n!)
```

permutation generation.

Do NOT brute-force all possible shipment sequences.

The implementation should be approximately polynomial and suitable for real-world shipment counts.

Use:

```text
candidate generation
→ scoring
→ bounded look-ahead
→ greedy selection
→ local improvement
```

instead.

The goal is a strong practical solution, not mathematically perfect global optimization.

# 33. Important invariants

The following rules must NEVER be violated:

```text
1. Vehicle load can never be negative.

2. Vehicle load can never exceed vehicleCapacity.

3. A delivery cannot occur without enough boxes.

4. A collection cannot occur if it causes capacity overflow.

5. A shipment cannot appear twice in the final route.

6. Numbered routes must include every required shipment.

7. Mixed routes may select a subset.

8. Every route starts at DEPOT.

9. Every depot visit must have a valid reason.

10. Every final route stop must have a valid location.

11. Route optimization must terminate.

12. No brute-force permutation of all shipments.
```
